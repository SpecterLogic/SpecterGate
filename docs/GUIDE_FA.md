# راهنمای سادهٔ فارسی SpecterGate؛ از نصب تا دریافت کانفیگ

در این آموزش هیچ دامنه، IP، رمز ورود یا مسیر دسترسیِ نصب واقعی درج نشده است. تمام آدرس‌ها نمونه‌اند و باید آن‌ها را با اطلاعات سرور خودتان جایگزین کنید.

## فهرست

۱. آماده‌سازی سرور و DNS<br>
۲. نصب پنل و دریافت مشخصات ورود<br>
۳. ورود با پورت جدا و مسیر تصادفی<br>
۴. ساخت اولین کانفیگ VLESS/Reality<br>
۵. ساخت کاربر، ساب و QR<br>
۶. محدودیت دسترسی کاربران و گروه‌ها<br>
۷. ساخت XHTTP/TLS و سایر پروتکل‌ها<br>
۸. مسیریابی، WARP، DNS و نودها<br>
۹. ربات و بکاپ<br>
۱۰. مدیریت، به‌روزرسانی و رفع اشکال

---

## ۱. چه چیزهایی لازم است؟

- یک سرور اختصاصی برای این پنل، با دسترسی `root` یا `sudo`.
- Ubuntu 24.04 یا جدیدتر، یا Debian 12 یا جدیدتر؛ Python باید حداقل 3.11 باشد.
- برای شروع، سروری با حدود ۲ گیگابایت RAM و فضای کافی برای سیستم و لاگ‌ها مناسب است؛ مصرف واقعی به تعداد کاربران و ترافیک بستگی دارد.
- یک دامنه که بتوانید DNS آن را تغییر دهید.
- دسترسی سرور به GitHub، مخزن بسته‌های سیستم‌عامل، npm و PyPI.
- باز بودن TCP پورت‌های ۸۰ و ۴۴۳ برای وب و صدور/تمدید گواهی؛ پورت SSH و پورت‌های اتصال کاربران را هم متناسب با تنظیمات خود باز نگه دارید.

اگر روی سرور پنل یا سرویس دیگری دارید، ابتدا از آن بکاپ بگیرید. نصب‌کننده برای یک سرور اختصاصی طراحی شده و تنظیمات Nginx پیش‌فرض را تغییر می‌دهد.

### معنی نام‌ها

| نام     | کاربرد                                                         |
| ------- | -------------------------------------------------------------- |
| پنل     | محیط ورود مدیر و ساخت کاربر                                    |
| اینباند | روش ورود اتصال کاربران؛ مثلاً VLESS با Reality                 |
| کاربر   | حساب دارای حجم، انقضا و دسترسی مشخص                            |
| ساب     | یک لینک که کلاینت با آن کانفیگ‌های مجاز کاربر را دریافت می‌کند |
| نود     | سرور اجراکنندهٔ کانفیگ‌ها                                      |
| خروجی   | مسیر خروج ترافیک، مانند Direct یا WARP                         |

## ۲. اتصال به سرور و تنظیم DNS

از ترمینال کامپیوتر یا نرم‌افزار SSH وارد سرور شوید:

```bash
ssh root@your-server-ip
```

عدد بالا IP نمونه است. IP و رمز را از ارائه‌دهندهٔ سرور بگیرید. هنگام نوشتن رمز در ترمینال معمولاً چیزی دیده نمی‌شود؛ این طبیعی است.

برای یک نصب ساده، این رکورد را در DNS دامنه بسازید:

| نوع | نام نمونه         | مقدار نمونه    |
| --- | ----------------- | -------------- |
| A   | panel.example.com | your-server-ip |

برای تفکیک دامنه‌ها می‌توانید دو رکورد دیگر هم بسازید:

| نوع | نام نمونه       | کاربرد                          |
| --- | --------------- | ------------------------------- |
| A   | vpn.example.com | آدرس سرور در کانفیگ‌های کاربران |
| A   | sub.example.com | دامنهٔ جدا برای اشتراک          |

هر سه رکورد باید به IP سرور مربوط اشاره کنند. صرف ساخت رکورد DNS، سایت ساب یا گواهی آن دامنه را راه‌اندازی نمی‌کند؛ نصب ساده با یک دامنه کامل می‌شود و تفکیک وب‌سرور مرحلهٔ جداگانه است.

برای شروع، پراکسی CDN را خاموش و رکوردها را روی حالت **DNS only** بگذارید. به‌خصوص Reality را بدون تنظیمات سازگار پشت پراکسی HTTP معمولی قرار ندهید.

بررسی کنید دامنه به IP درست می‌رسد:

```bash
getent ahostsv4 panel.example.com
```

اگر رکورد IPv6 یا AAAA دارید، باید به IPv6 درست و قابل‌دسترسی همین سرور اشاره کند؛ رکورد اشتباه می‌تواند صدور SSL و اتصال را خراب کند.

## ۳. نصب سریع با آدرس مدیریت خصوصی

این دستور را پس از جایگزین‌کردن دامنه اجرا کنید:

```bash
curl -fsSLo /tmp/spectergate-install.sh https://raw.githubusercontent.com/SpecterLogic/SpecterGate/main/install.sh && sudo bash /tmp/spectergate-install.sh --domain panel.example.com --private-panel
```

نصب‌کننده برنامه، Xray، Nginx و گواهی HTTPS را نصب می‌کند. سپس برای پنل یک پورت آزاد و یک مسیر تصادفی می‌سازد. نام کاربری و رمز اولیه هم تصادفی‌اند.

اگر پورت مدیریت مشخصی می‌خواهید، مثلاً پورت نمونهٔ ۳۸۰۸۰:

```bash
sudo bash /tmp/spectergate-install.sh --domain panel.example.com --private-panel --panel-port 38080
```

پورت انتخابی باید آزاد باشد. پورت‌های SSH، وب، API داخلی و پورت اینباندها را برای مدیریت انتخاب نکنید.

### انتخاب دیتابیس

پیش‌فرض SQLite است و برای شروع به نصب دیتابیس جدا نیاز ندارد. برای PostgreSQL محلی:

```bash
sudo bash /tmp/spectergate-install.sh --domain panel.example.com --private-panel --database postgresql
```

این گزینه مخصوص نصب تازه است؛ دیتابیس موجود را به PostgreSQL تبدیل نمی‌کند. MySQL، MariaDB و TimescaleDB در نصب‌کنندهٔ فعلی گزینهٔ آماده ندارند.

برای نصب یک نسخهٔ موجود مشخص می‌توانید `--version TAG_OR_COMMIT` اضافه کنید. مقدار `TAG_OR_COMMIT` را واقعاً با یک تگ یا شناسهٔ commit موجود جایگزین کنید.

### بعد از پایان نصب

این موارد را از خروجی ترمینال نگه دارید:

- نام کاربری مالک؛
- رمز اولیه؛
- آدرس کامل پنل، شامل `https://`، دامنه، پورت، مسیر تصادفی و `/` آخر.

شکل آدرس شبیه این است؛ **این آدرس نمونه کار نمی‌کند**:

```text
https://panel.example.com:38080/RANDOM_ACCESS_PATH/
```

اگر فایروال ارائه‌دهندهٔ سرور جداست، پورت مدیریت را آنجا نیز باز کنید. ابزار تنظیم دسترسی، در صورت فعال‌بودن UFW سرور، پورت انتخابی را در آن باز می‌کند؛ فایروال بیرونی را تغییر نمی‌دهد.

## ۴. اگر پنل قبلاً نصب شده است

در نسخه‌ای که ابزار دسترسی خصوصی را دارد، روی خود سرور اجرا کنید:

```bash
sudo python3 /opt/spectergate/deploy/panel_access.py --domain panel.example.com
```

یا پورت دلخواه را مشخص کنید:

```bash
sudo python3 /opt/spectergate/deploy/panel_access.py --domain panel.example.com --port 38080
```

این ابزار به گواهی معتبر همان دامنه نیاز دارد، رابط مدیریت را برای مسیر جدید می‌سازد، مسیر API و کوکی را تنظیم می‌کند و مشخصات ورود را تغییر نمی‌دهد. اگر قبلاً مسیر ساخته شده باشد، اجرای دوباره همان مسیر را نگه می‌دارد.

آدرس پایه و مسیرهای قدیمی مدیریت، صفحهٔ ورود یا API مدیریت را نمایش نمی‌دهند. مسیرهای عمومی اشتراک همچنان می‌توانند روی پورت ۴۴۳ در دسترس بمانند.

پورت و مسیر تصادفی، ورود دومرحله‌ای محسوب نمی‌شوند و جای رمز قوی یا HTTPS را نمی‌گیرند. آدرس مدیریت را فقط به مدیران بدهید و برای کاربران، ساب خودشان را بفرستید.

برای دیدن آدرس ذخیره‌شده، روی سرور:

```bash
sudo cat /etc/spectergate/panel-access.json
```

این فایل شامل مسیر خصوصی مدیریت است؛ آن را عمومی منتشر نکنید.

## ۵. ورود اول و بررسی سلامت

۱. آدرس کامل پنل را باز کنید.<br>
۲. نام کاربری و رمز اولیه را وارد کنید.<br>
۳. در «تنظیمات ← امنیت حساب»، رمز خودتان را تنظیم کنید.<br>
۴. در داشبورد، وضعیت هسته و نودها را ببینید.

اگر هنوز اینباندی نساخته و کانفیگی اعمال نکرده‌اید، متوقف‌بودن هسته به‌تنهایی به معنی خرابی نصب نیست.

دستورهای کاربردی:

```bash
spectergate status
spectergate logs
sudo spectergate restart
```

با `Ctrl+C` فقط نمایش زندهٔ لاگ متوقف می‌شود؛ خود سرویس خاموش نمی‌شود.

اگر مشخصات اولیه را گم کرده‌اید، مقادیر اولیه در فایل زیر هستند:

```bash
sudo nano /opt/spectergate/backend/.env
```

نام‌های مربوط:

```dotenv
SPECTERGATE_ADMIN_USERNAME=YOUR_INITIAL_USERNAME
SPECTERGATE_ADMIN_PASSWORD=YOUR_INITIAL_PASSWORD
```

اگر رمز را بعداً داخل پنل عوض کرده باشید، مقدار اولیهٔ این فایل دیگر رمز فعلی نیست. تغییر سادهٔ این فایل نیز رمز حساب موجود را بازنشانی نمی‌کند.

## ۶. اولین کانفیگ: VLESS با Reality

برای شروع، یک اینباند ساده بسازید:

۱. به **اینباندها ← اینباند جدید** بروید.<br>
۲. این مقادیر نمونه را وارد کنید:

| فیلد         | مقدار پیشنهادی برای شروع          |
| ------------ | --------------------------------- |
| نام نمایشی   | نام دلخواه، مثلاً Server Reality  |
| تگ یکتا      | vless-reality-01                  |
| پروتکل       | VLESS                             |
| نود میزبان   | نود محلی                          |
| پورت شنود    | 8443، اگر آزاد است                |
| آدرس شنود    | 0.0.0.0 برای اتصال مستقیم کاربران |
| شبکه         | RAW / TCP                         |
| لایه امنیت   | Reality                           |
| SNI          | نام یک مقصد پوششی واقعی و سازگار  |
| مقصد Reality | همان مقصد با پورت 443             |
| Flow         | xtls-rprx-vision                  |

مقصد پوششی باید واقعی و مناسب Reality باشد. نمونهٔ عمومی متداول `www.cloudflare.com` و مقصد `www.cloudflare.com:443` است؛ مناسب‌بودن مقصد را از سرور خودتان آزمایش کنید. **SNI پوششی، الزاماً دامنهٔ اختصاصی سرور شما نیست.**

برای تولید کلیدها دکمهٔ تولید را بزنید یا در ساخت اولیه آن‌ها را خالی بگذارید تا ساخته شوند. کلید خصوصی را برای کاربر نفرستید.

در **تنظیمات پیشرفته ← اشتراک**:

- «آدرس انتشار کانفیگ» را می‌توانید `vpn.example.com` بگذارید، به شرطی که DNS آن درست باشد.
- در اتصال مستقیم، «پورت انتشار» را خالی بگذارید تا همان پورت شنود استفاده شود.
- پورت انتشار را فقط وقتی متفاوت بگذارید که واقعاً پراکسی یا نگاشت پورت را تنظیم کرده‌اید.

اینباند را ذخیره کنید و **اعمال کانفیگ** را بزنید. نتیجه باید موفق باشد و هسته در حال اجرا بماند.

اگر UFW فعال است:

```bash
sudo ufw allow 8443/tcp
```

همین پورت را در فایروال ارائه‌دهنده هم باز کنید. پورت مدیریت پنل با پورت اینباند یکی نیست.

## ۷. ساخت کاربر، گرفتن ساب و QR

به **کاربران ← کاربر جدید** بروید:

۱. یک نام انگلیسی یکتا، مثلاً `user01` بنویسید.<br>
۲. سقف مصرف را مثلاً ۱۰ گیگابایت قرار دهید. در این فرم، صفر یعنی بدون محدودیت حجم.<br>
۳. تاریخ انقضا را انتخاب کنید؛ خالی یعنی بدون انقضا.<br>
۴. در کانفیگ‌های مجاز، اینباند ساخته‌شده را انتخاب کنید یا مجوز بالادست را به ارث ببرید.<br>
۵. کاربر را فعال نگه دارید و ذخیره کنید.

در فهرست کاربران، دکمهٔ **لینک** یا کپی لینک اشتراک را بزنید. صفحهٔ اشتراک امکان انتخاب فرمت، کپی لینک و نمایش QR را دارد.

کاربر باید ساب خودش را در کلاینت وارد و آن را به‌روزرسانی کند. آدرس مدیریت پنل، لینک ساب نیست.

برای کلاینت‌های مبتنی بر Xray از نسخهٔ به‌روز استفاده کنید؛ برای نمونه [v2rayNG در Android](https://github.com/2dust/v2rayNG) یا [v2rayN در Windows](https://github.com/2dust/v2rayN). سازگاری یک کانفیگ به هسته و نسخهٔ کلاینت بستگی دارد؛ همهٔ فرمت‌ها همهٔ انتقال‌ها را پوشش نمی‌دهند.

برای XHTTP و mKCP، اگر لینک یا فرمت دیگر سازگار نبود، از خروجی کامل **Xray JSON** با کلاینت سازگار استفاده کنید. برای نمونه، خروجی Sing-box پنل، اینباندهای XHTTP و mKCP را شامل نمی‌شود.

### تست اتصال

- ابتدا با یک کاربر فعال و دارای حجم باقی‌مانده تست کنید.
- کانفیگ را در کلاینت انتخاب کنید و یک سایت HTTPS باز کنید.
- IP خروجی را بررسی کنید؛ باید IP مسیر خروج سرور باشد.
- در پنل، همگام‌سازی آمار را بزنید و افزایش مصرف را ببینید.
- «اعمال کانفیگ موفق» فقط اعتبار کانفیگ را نشان می‌دهد؛ بازشدن سایت از داخل کلاینت، تست واقعی اتصال است.

## ۸. هر کاربر یا گروه به کدام کانفیگ‌ها دسترسی داشته باشد؟

در ساخت یا ویرایش کاربر، بخش **دسترسی به کانفیگ‌ها و تونل‌ها** را باز کنید:

- **همه موارد مجاز در سطح بالادست**: دسترسی را از مدیر و گروه می‌گیرد.
- **فقط موارد انتخابی**: فقط اینباندها یا تونل‌های تیک‌خورده مجازند.
- اگر حالت انتخابی باشد ولی چیزی انتخاب نکنید، دسترسی به آن نوع منبع بسته است.

برای گروه، در **اشتراک‌های گروهی** یک گروه بسازید، سقف عضو و حجم مشترک را تعیین کنید و اعضا را اضافه کنید. گروه هم محدودیت منابع مستقل دارد.

مثال: گروه فقط اینباند A را مجاز کرده و کاربر فقط B را انتخاب کرده است. نتیجه هیچ‌کدام است؛ انتخاب کاربر محدودیت گروه را باز نمی‌کند. مدیر بالادستی نیز می‌تواند محدوده را محدود کند.

پس از تغییر دسترسی، ساب کلاینت را به‌روزرسانی کنید. هستهٔ محلی، تغییر حساب‌ها و سهمیه‌ها را دوره‌ای همگام می‌کند؛ اعمال دستی برای بررسی فوری هم در دسترس است.

مقدار «محدودیت دستگاه» فعلاً ذخیره می‌شود؛ روی اجرای سخت‌گیرانهٔ تعداد دستگاه/HWID حساب نکنید.

## ۹. VLESS + XHTTP + TLS

این روش به گواهی معتبر برای دامنهٔ کانفیگ نیاز دارد. برای نمونه، بعد از درست‌بودن DNS دامنهٔ `vpn.example.com`:

```bash
sudo certbot certonly --webroot -w /var/www/html -d vpn.example.com
```

چالش HTTP باید از اینترنت روی پورت ۸۰ به همین سرور برسد. نصب‌کنندهٔ عادی مسیر چالش را آماده می‌کند؛ اگر Nginx را تغییر داده‌اید، مسیر چالش را نیز بررسی کنید.

فایل خصوصی Let's Encrypt را به‌صورت عمومی قابل‌خواندن نکنید. یک کپی محافظت‌شده برای حساب سرویس بسازید:

```bash
sudo install -d -o spectergate -g spectergate -m 0700 /opt/spectergate/backend/data/certificates
sudo install -o spectergate -g spectergate -m 0600 /etc/letsencrypt/live/vpn.example.com/fullchain.pem /opt/spectergate/backend/data/certificates/vpn-cert.pem
sudo install -o spectergate -g spectergate -m 0600 /etc/letsencrypt/live/vpn.example.com/privkey.pem /opt/spectergate/backend/data/certificates/vpn-key.pem
```

یک اینباند دیگر بسازید:

| فیلد              | مقدار نمونه                                             |
| ----------------- | ------------------------------------------------------- |
| پروتکل            | VLESS                                                   |
| شبکه              | XHTTP                                                   |
| امنیت             | TLS                                                     |
| پورت              | 9443، متفاوت از اینباند قبلی                            |
| SNI و آدرس انتشار | vpn.example.com                                         |
| Path              | یک مسیر دلخواه مثل /connect                             |
| گواهی TLS         | /opt/spectergate/backend/data/certificates/vpn-cert.pem |
| کلید TLS          | /opt/spectergate/backend/data/certificates/vpn-key.pem  |
| ALPN              | h2,http/1.1                                             |
| حالت XHTTP        | برای شروع auto                                          |

XTLS Flow مخصوص RAW/TCP را روی این کانفیگ نگذارید. ذخیره، اعمال و سپس پورت را باز کنید:

```bash
sudo ufw allow 9443/tcp
```

برای تمدید گواهی، کپی‌های سرویس هم باید به‌روز شوند. یک hook بسازید؛ **دامنهٔ نمونه را در آن نیز جایگزین کنید**:

```bash
sudo nano /etc/letsencrypt/renewal-hooks/deploy/spectergate-vpn
```

محتوا:

```sh
#!/bin/sh
set -eu
if [ "$RENEWED_LINEAGE" = "/etc/letsencrypt/live/vpn.example.com" ]; then
    install -o spectergate -g spectergate -m 0600 "$RENEWED_LINEAGE/fullchain.pem" /opt/spectergate/backend/data/certificates/vpn-cert.pem
    install -o spectergate -g spectergate -m 0600 "$RENEWED_LINEAGE/privkey.pem" /opt/spectergate/backend/data/certificates/vpn-key.pem
    systemctl try-restart spectergate
fi
nginx -t && systemctl reload nginx
```

بعد:

```bash
sudo chmod 700 /etc/letsencrypt/renewal-hooks/deploy/spectergate-vpn
sudo certbot renew --dry-run
```

ری‌استارت سرویس ممکن است اتصال‌های جاری را کوتاه‌مدت قطع کند.

## ۱۰. VLESS + XHTTP + Reality و سایر پروتکل‌ها

### XHTTP + Reality

مانند اینباند Reality قبلی بسازید، ولی شبکه را XHTTP بگذارید، پورت متفاوتی انتخاب کنید و Path تنظیم کنید. برای شروع حالت XHTTP را `auto` بگذارید. Flow را خالی نگه دارید. کلید و Short ID مربوط به همین اینباند باشند و مقصد پوششی را با اتصال واقعی آزمایش کنید.

### Trojan

پروتکل Trojan، شبکه TCP و امنیت TLS را انتخاب کنید. SNI و گواهی/کلید معتبر لازم است. پورت آزاد متفاوتی بگذارید، ذخیره و اعمال کنید و ساب کاربر را تازه کنید.

### VMess

پروتکل VMess را انتخاب کنید. برای WebSocket، Path و در صورت نیاز Host را تنظیم کنید. اگر TLS فعال می‌کنید، SNI و گواهی درست را هم وارد کنید. این ترکیب نیز پورت شنود مستقل لازم دارد، مگر پراکسی مناسب را جدا تنظیم کرده باشید.

### Shadowsocks

پروتکل Shadowsocks را انتخاب کنید. برای حالت ساده، شبکه TCP و لایهٔ امنیت `none` را بگذارید؛ رمزگذاری خود Shadowsocks برقرار است و این گزینه به معنی خاموش‌کردن رمزگذاری Shadowsocks نیست. پنل در این حالت از `chacha20-ietf-poly1305` استفاده می‌کند.

برای Shadowsocks با انتقال یا TLS سفارشی، خروجی سادهٔ `ss://` همهٔ اطلاعات را منتقل نمی‌کند؛ از خروجی سازگار Xray JSON استفاده کنید. پشتیبانی UDP را جداگانه با کلاینت و فایروال خود بسنجید.

### mKCP و تنظیمات پیشرفته

mKCP انتقال UDP است و خروجی سازگار Xray JSON لازم دارد. پورت UDP آن باید باز باشد. تنظیمات MTU، ظرفیت و بافر دو سمت باید سازگار باشند. این سناریو را پیش از استفادهٔ عمومی جداگانه تست کنید.

در نسخهٔ فعلی، سرور AmneziaWG، سرور WireGuard و OpenVPN پیاده‌سازی نشده‌اند. WARP خروجی است و جای سرور AmneziaWG را نمی‌گیرد.

## ۱۱. پورت داخلی و پورت عمومی ۴۴۳

اگر کانفیگ روی `127.0.0.1:18443` گوش می‌دهد ولی در ساب پورت ۴۴۳ نوشته‌اید، باید یک پراکسی واقعاً ترافیک ۴۴۳ را به ۱۸۴۴۳ برساند. تغییر «پورت انتشار» به‌تنهایی چنین مسیری ایجاد نمی‌کند.

اشتراک چند سرویس روی ۴۴۳ با Nginx Stream/SNI یک تنظیم پیشرفته است: مقصد SNI، TLS passthrough، دریافت PROXY protocol و فایروال باید هماهنگ باشند. در حالت عادیِ مستقیم، پورت شنود و انتشار را برابر نگه دارید و PROXY protocol را خاموش بگذارید.

دامنهٔ ساب جدا نیز به سایت HTTPS خودش نیاز دارد که `/sub/`، `/s/` و فایل‌های لازم را سرو کند. API مدیریت نباید صرفاً با تغییر دامنه در تنظیمات، روی آن عمومی شود.

## ۱۲. مسیریابی و WARP

در **مسیریابی و WARP** ابتدا نود را انتخاب کنید:

- `Direct`: خروج از اینترنت خود سرور.
- `WARP`: خروج از حساب WireGuard/WARP تنظیم‌شده.
- `Block`: مسدودکردن ترافیک.
- `IPv4`: خروج با راهبرد IPv4.

برای WARP باید مشخصات حساب معتبر خودتان را داشته باشید: Private Key، Public Key سمت مقابل، Endpoint، آدرس‌های تونل و Reserved. پنل حساب WARP را خودکار ثبت نمی‌کند.

برای مثال، می‌توانید یک قانون برای `domain:example.org` بسازید و خروجی را WARP بگذارید. قواعد به ترتیب بررسی می‌شوند و شروط داخل یک قانون با هم ترکیب می‌شوند. برای حالت «این دامنه یا آن IP»، دو قانون جدا بسازید.

قواعد API داخلی و مسدودسازی IPهای خصوصی پیش از قواعد دلخواه قرار دارند. گزینه‌های `geoip:` و `geosite:` به فایل دادهٔ مناسب روی همان نود نیاز دارند. تشخیص BitTorrent نیز به Sniffing فعال و ترافیک قابل‌تشخیص وابسته است.

## ۱۳. تونل DNS و نود راه دور

در بخش تونل‌های DNS می‌توانید پروفایل DNSTT/NoizDNS و تنظیم Multiplexer بسازید. دکمهٔ راه‌اندازی، رکوردهای DNS و دستورهای لازم را نشان می‌دهد. صرف ذخیرهٔ پروفایل، برنامهٔ تونل و رکوردهای A/NS را روی سرور و DNS نصب نمی‌کند.

در بخش نودها، نود را اضافه و راهنمای اتصال agent را باز کنید. کلید agent خصوصی است. عامل روی سرور نود نصب می‌شود و تنظیمات را دریافت می‌کند. دسترسی کاربر/گروه و تخصیص اینباند به نود را درست تنظیم کنید. برای جزئیات به [راهنمای agent](../agent/README.md) مراجعه کنید.

## ۱۴. ربات: ساخت کاربر و بکاپ مالک

هر نصب باید ربات خودش را داشته باشد:

۱. با BotFather ربات بسازید و توکن بگیرید.<br>
۲. مالک و مدیران مجاز، گفت‌وگوی خصوصی با ربات را شروع کنند.<br>
۳. در **ربات و بکاپ**، توکن و شناسهٔ عددی حساب تلگرام مالک را وارد کنید.<br>
۴. یک رمز بکاپ جدا، حداقل ۱۶ کاراکتر، انتخاب و بیرون پنل نگه دارید.<br>
۵. اتصال را بررسی و سپس ربات را فعال کنید.<br>
۶. برای هر مدیر، شناسهٔ عددی تلگرام را به حساب پنلش وصل کنید و در صورت نیاز اجازهٔ ساخت کاربر بدهید.

نام کاربری `@...` جای شناسهٔ عددی حساب نیست. شناسهٔ گروه را هم به جای مالک وارد نکنید.

نمونهٔ فرمان‌ها:

```text
/new user02 30 10
/sub user02
/backup
```

فرمان اول کاربر ۳۰روزه با ۱۰ GiB می‌سازد و ساب/QR می‌فرستد. اگر حساب مدیر به پلن نیاز دارد، شناسهٔ پلن را به انتهای فرمان اضافه کنید. سهمیه و محدودهٔ دسترسی مدیر همچنان اعمال می‌شوند.

`/backup` فقط برای مالک است؛ بکاپ دوره‌ای هم فقط به مالک تعیین‌شده ارسال می‌شود. فروش خودکار یا پرداخت در ربات وجود ندارد.

## ۱۵. بکاپ و بازیابی

از داخل پنل می‌توانید بکاپ رمزگذاری‌شده دانلود کنید. از ترمینال نیز:

```bash
sudo spectergate backup /root/panel.sgbackup
```

رمز در ترمینال پرسیده می‌شود. برای رمزگشایی:

```bash
sudo spectergate decrypt-backup /root/panel.sgbackup /root/panel.tar.gz
```

خروجی نباید از قبل وجود داشته باشد. رمزگشایی فقط فایل آرشیو می‌سازد و آن را خودکار روی سیستم استخراج نمی‌کند.

بکاپ شامل دیتابیس سازگار، اطلاعات manifest، کلید رمزگذاری تنظیمات در صورت وجود و کانفیگ تولیدشدهٔ محلی Xray است. فایل `.env`، گواهی‌های TLS، تنظیمات Nginx، کل سرور و دیسک نودها خودکار داخل آن نیستند؛ آن‌ها را جدا و امن نگه دارید. سقف ارسال بکاپ ۴۸ MiB است.

برای بازیابی SQLite روی یک نصب هم‌نسخه و ایزوله:

۱. پنل را متوقف کنید: `sudo spectergate stop`.<br>
۲. آرشیو رمزگشایی‌شده را در یک پوشهٔ خالی بررسی و استخراج کنید.<br>
۳. دیتابیس مقصد فعلی را جداگانه بکاپ بگیرید.<br>
۴. snapshot دیتابیس را در مسیری بگذارید که `SPECTERGATE_DATABASE_URL` نصب مقصد نشان می‌دهد.<br>
۵. کلید `secrets.key` را، اگر در آرشیو است، به مسیر `backend/data/secrets.key` برگردانید.<br>
۶. `.env` معتبر، گواهی‌ها و دسترسی فایل‌ها را بازسازی کنید؛ مالک فایل‌های داده `spectergate` و مجوز فایل‌های حساس ۶۰۰ باشد.<br>
۷. سرویس را راه بیندازید و ورود، لینک‌ها و اتصال را بررسی کنید.

اگر `secrets.key` را بازیابی نکنید، تنظیمات رمزگذاری‌شدهٔ قدیمی مثل توکن ربات قابل رمزگشایی نیستند. فایل‌های WAL/SHM دیتابیس قبلی را با snapshot جدید مخلوط نکنید؛ جایگزینی را فقط در حالت توقف کامل انجام دهید.

برای PostgreSQL از `pg_restore` و dump مخصوص آن استفاده کنید؛ فایل آن SQLite نیست. بازیابی را قبل از اتکای عملی، روی یک محیط جدا تمرین کنید. بدون رمز بکاپ، آرشیو رمزگذاری‌شده قابل بازیابی نیست.

## ۱۶. مدیریت روزانه و به‌روزرسانی

```bash
spectergate status
spectergate logs
sudo spectergate restart
sudo spectergate stop
sudo spectergate start
sudo nginx -t
sudo certbot renew --dry-run
```

مسیرها:

| مورد              | مسیر                               |
| ----------------- | ---------------------------------- |
| برنامه            | /opt/spectergate                   |
| تنظیمات اولیه     | /opt/spectergate/backend/.env      |
| دادهٔ محلی        | /opt/spectergate/backend/data      |
| آدرس خصوصی مدیریت | /etc/spectergate/panel-access.json |
| تنظیم وب‌سرور     | /etc/nginx/sites-available/        |

هستهٔ دارای کانفیگ اعمال‌شده، پس از ری‌استارت سرویس بازیابی می‌شود. اگر هسته را از پنل عمداً متوقف کرده باشید، توقف حفظ می‌شود تا دوباره راه‌اندازی یا اعمال کنید.

پیش از ارتقا، بکاپ و نسخهٔ امن `.env`، گواهی‌ها و Nginx را نگه دارید. اجرای دوبارهٔ نصب‌کننده فایل `.env` و داده را حفظ می‌کند، ولی Nginx را دوباره می‌سازد؛ تنظیمات دستی تفکیک دامنه/SNI ممکن است نیاز به بازاعمال داشته باشند. نسخهٔ مشخص را انتخاب کنید و قبل از ارتقای عمومی روی یک نصب تست بسنجید. مهاجرت عمومی نسخه‌بندی‌شدهٔ تمام تغییرات دیتابیس هنوز وجود ندارد.

| SSL خطا دارد                        | تطبیق دامنه، تاریخ سرور، اعتبار گواهی، مسیر گواهی و تمدید را بررسی کنید                       |

گزارش خطا را قبل از انتشار از توکن ربات، کلید خصوصی، رمز، لینک ساب و مسیر خصوصی مدیریت پاک کنید. داشتن گزینه در فرم یا قبولی تست کانفیگ، تضمین اتصال روی تمام شبکه‌ها نیست.

برای وضعیت دقیق قابلیت‌ها و بخش‌های هنوز پیاده‌سازی‌نشده، [جدول پوشش قابلیت‌ها](FEATURE_PARITY.md) را ببینید.
